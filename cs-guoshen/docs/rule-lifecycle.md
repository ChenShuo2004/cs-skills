# 规则会变：保留时间与证据

规则文件是审核问题和依据索引，不是永久处罚表。版本号记录本项目修订，`effective_from/to` 记录有证据的适用期（含首尾日期）；未知写 null，不能用我们查阅的日期代替官方生效日期。

`last_verified` 是最近实际核对日期；`review_after` 是建议复核日期，不是官方失效日。只改文件排版不能更新核实日期。超过复核日期仍展示条目并标记待复核，避免检查盲区。

## 状态与依据分别管理

- `candidate`：新提议，尚未接受。
- `verification_needed`：正文缺失、规则疑似变化或关键条件未证实。
- `active`：进入当前检查流程；仍须核来源、语境和时间，不代表命中就违规。
- `superseded` / `retired`：被新版替代或停止使用，保留历史。

依据类型：`official` 表示依据官方资料，但必须继续查看每条来源的“官方全文/入口/转述”等实际获取状态；`source_pending` 表示未取得依据；`case_observation` 是案例观察；`method` 是检查方法。观察可以被多个真实案例支持，但不能因此自动改为官方规则。模拟案例不能成为规则依据。

## 修订流程

1. 提交来源或匿名案例，记录平台、投稿/加热等场景、日期、通知、修改和反例。
2. 分析共性，列出其他解释和适用边界，先提候选。不要仅统计拒审样本；加入通过、申诉及复现失败的记录。
3. 核对现行官方正文及版本日期。无法核实时保留待核，不用第三方旧转载补成确定结论。
4. 修订现有规则前，将原始条目原样保存至 `resources/rules/history/<ID>-v<版本>.json`。同一ID版本递增，新条目 `supersedes` 填 `ID@旧版本`；不改写旧证据。新ID首次版本为1。
5. 更新适用范围、依据、例外、建议复核日、关联真实案例和规则集版本；附变更说明与必要测试，通过 PR 人工复核后合并。

当前上下文脚本选择当前规则集，并筛选日期、场景和状态；**不会自动重建历史规则集**。历史审核须人工读取存档与对应 Git 提交，缺版本时明确无法还原。第一次发布的规则多数生效区间未知，不能回填猜测日期。

## 新增平台或识别工具

平台先在 `resources/rules/index.json` 登记名称、规则文件和指南，再扩充规则/案例格式中的平台枚举，补隔离测试。共用提取流程，不复制整套技能。新工具输出须保持 `evidence.json` 的通道、原文、时间结构，具体契约见 [现有提取实现](../scripts/extract_video.py)；保留工具失败和覆盖数据，不把失败写成空内容成功。

运行 [校验脚本](../scripts/validate_framework.py) 检查格式、时间、来源和案例引用。人工复核仍需核正文、事实、隐私与适用性；自动校验通过不是事实认证。
